# SV_SOUL：从事实回答到有个性的 NPC 对话

调研日期：2026-11-06。本文是源码诊断与下一轮改进建议；没有替换生产提示词、改变游戏配置，也没有把下面的写作样例当作模型实测结果。

## 结论

保留现有事实、时间和记忆底座，在其上加入角色表达层：经过原版校准的角色写作、短示例对话、当前关注点、对话意图和有延续性的心境。第一阶段仍保持每轮一次回复请求。先以 Abigail 做对照评测，再推广到其余角色。

NPC 应当能答对信息，也应当有偏好、判断、顾虑、愿望和表达方式。原版台词即使固定，也体现这些设计；增加记忆框架不会自动补上它们。

## 当前代码诊断

可直接观察到的实现：

- `Agents/NPCAgent.cs::BuildSystemPrompt` 首先拼接一整段权威规则和完整世界 JSON，再添加 Character、Voice、背景与记忆。
- CoreTraits 是概括性的性格/兴趣说明；Voice 只是“自然、简洁、不要像通用助手”，没有可学习的具体语言样本。
- 五个 NPC 的婚后阶段表达基本使用同一模板，只要求亲近和事实正确。
- `MoodResponses` 仅选择下雨或下雪的静态参考句，没有持续的情境心态；night 配置尚未被这一分支使用。
- 没有“这句话想安慰、调侃、拒绝、分享还是确认”的意图，也没有角色自己的当前关注点。
- 开场白固定为“你好，想聊些什么？”。语气在用户开口前就偏向问答助手。
- 当前 Interpretation 主要归纳玩家互动特点，并没有真正建立 NPC 自己的情绪轨迹。
- 上一轮用婚姻、住址、婚礼日期验收，证明事实正确，但不构成角色表现验收。

工程判断：上述输入结构会鼓励模型做简洁的信息复述，是当前输出风格的可能主因；需要对照实验确认各改动的贡献。JSON 本身并非必然导致机械回复，事实准确也与情感表达兼容。

- [Inworld 官方迁移说明](https://docs.inworld.ai/character-studio-deprecation) 确认旧 Character Studio 已停止提供，现使用 Runtime SDK 和模板，不应建议重新依赖旧 Studio。

- [RoleLLM](https://arxiv.org/abs/2310.00746) 区分角色知识与说话风格；[PsyPlay](https://arxiv.org/abs/2502.03821) 关注更深层人格倾向；[RPEval](https://arxiv.org/abs/2505.13157) 从情绪理解、决策和角色一致性等维度评测。这里只借鉴机制与评价维度。

## 建议的表达层

### 1. 从标签人设升级为行为人设

为每个 NPC 编写：核心欲望、在意的事、容易触动的点、表达亲近的方式、表达分歧的方式、语言节奏和不符合角色的表现。

Abigail 的初始写作方向：向往冒险与自主；对奇异事物好奇；亲近时可以调侃、分享兴奋或邀请玩家参与兴趣；需要时也能认真、安静、担心。婚后保留这些特质，而不是只剩配偶身份。具体设定先对照当前游戏原版对话和剧情校准，避免把现有人设卡的自行扩写当成已确认原作设定。

用运行时合法加载的原版/已安装内容修补后的对话做语言校准来源，保留语言、关系阶段和情境标签。原版台词作为风格参照，不作为当前存档已经发生的经历；不发布整套游戏文本。不把控制符、条件标记直接塞进模型。

建议每个角色先编写12组短样例，覆盖熟悉/陌生、安慰、调侃、拒绝、兴趣、婚后相处等情境；每轮按情境选择2–3组，明确它们是虚构风格样例而非历史证据。

### 2. 给角色当前关注点与对话意图

小型状态足够，不引入多 Agent 辩论或大型心理模拟：

- 当前心境及触发来源，如被关心后的放松、谈起冒险时兴奋。
- 当前关注点，例如还惦记着冒险、想分享游戏兴趣；表达为愿望，不虚构已执行行动。
- 对玩家的当前态度，受真实关系、近期经历和当前谈话共同影响。
- 未结束话题或约定，带来源与游戏时间。

当前消息到来时，在同一次生成中决定一个主要对话意图：回应、安慰、调侃、表达分歧、分享想法、确认或自然结束。不要求每句话都问问题、叫昵称或提自己的标志性爱好。

第一步可仅在提示中组织这些线索，让模型生成自然台词；第二步再增加简短的结构化状态增量。结构化增量解析失败时保留可用台词，状态保持原值，不向玩家显示 JSON 或分析过程。

### 3. 事实约束与表达自由分开

必须有依据：婚姻、住所、孩子、赠礼、婚礼日期、既往共同经历、已经完成的动作。

允许角色生成：此刻的感受、对眼前事情的看法、幽默、犹豫、审美偏好、愿望和有条件的提议。这些分别标为主观态度或意图，不升级为已发生的游戏事件。

NPC 可以有独立意见。亲密关系不等于每次都赞同玩家，也不等于每轮都甜言蜜语。情绪要有上下文连续性，不能随机跳变；不能只用“低好感=冷淡、高好感=热情”决定全部表达。

### 4. 将数据库视图转换为对话情境

完整快照和证据仍由程序保留。对话提示只提供本轮必要事实，以及可自然表达的关系语义；记录 Id、调试字段、分数等留在诊断数据中。

例如内部仍有 Married、14心和 FarmHouse，但表达上下文可写成：你与玩家已经结婚，关系亲密，共同住在农场；当前面对面聊天。具体婚期只在问题相关时加入。保留“玩家说过”“亲历事件”“主观理解”等来源区别。

为角色声音与样例保留固定上下文份额，减少低相关状态堆积；后台记忆机制和事实优先级不变。现有总预算内重新分配，不默认扩大上下文。

### 5. 情感记忆记录事情的意义

在原有事实外，允许记录有来源的主观意义：玩家在角色表达担忧时如何回应、某次交流为何让角色更愿意分享、尚未回应的约定是什么。

主观意义与原事件分别保存；它可以影响以后的语气，不能回写游戏婚姻或好感度，也不能让所有 NPC 共享私人感受。对话中的一次轻松情绪不立即改写长期人格。只在确有互动意义时由现有后台任务更新，不追加每轮反思调用。

### 6. 改掉助手式交互惯性

替换固定“你好，想聊些什么？”：根据角色、时刻、近期话题选择或生成简短开场；重复打开窗口可接续上次话题。

通常保持原版对话框适合的短句或短段落，但不要用硬性1–3句压平所有情境；直接问题可以直答，安慰也可以短暂安静，分歧可以说明缘由。不会把“更有情感”做成更长、更多省略号、更多表情或重复撒娇。

## 写作样例：仅展示方向

以下是新写的候选台词，不是原版引用，也不是实测输出。已婚、共同住所、婚期均以现有测试存档为前提。

玩家：我们现在是什么关系？住在哪里？

旧风格：我们是夫妻。我们住在荔枝农场。

候选：我们都结婚了，你还问呀？荔枝农场就是我们的家。怎么，今天想考考我？

玩家：今天别去矿洞了，陪我待会儿。

候选：可以陪你一会儿。至于矿洞……我可还没死心。要不要来一局游戏？

后一句是角色的邀请，不意味着系统真的启动了小游戏。没有对应游戏能力时，不得说“我已经帮你启动了”。

玩家：今天好累，不想说话。

候选：那就先别说了。我在这儿，等你想聊的时候再聊。

语气是否符合原版，需要对照原版与盲评调整；不能把上述例句设为固定回复。

## 可决策路线

| 路线 | 延迟/依赖 | 收益和代价 | 建议 |
|---|---|---|---|
| 角色写作＋情境视图＋精选样例 | 仍一次模型请求，无新服务 | 最直接改善声音；长期心境延续有限 | 先做 |
| 加入轻量对话状态和情感意义 | 同次回复或现有后台任务更新 | 改善连续性、自主意见和未完话题；需要状态验证 | 第二步 |
| 每轮规划→写作→审稿多模型 | 至少新增串行调用 | 控制更细，但会拖慢互动且多处故障 | 暂不采用 |
| 替换角色云平台/训练角色模型 | 新运行体系或训练维护成本 | 可能提高角色表现，须本地评测 | 前两步达不到目标再考虑 |

不优先靠提高 temperature 解决。当前未发送 temperature 不等于 temperature=0；采样参数不能补出缺失的角色写作与动机。先固定当前模型和请求参数做对照，再单独评估模型的角色扮演适配度。

## 下一轮评测

先以 Abigail 做三个版本：当前基线、加入原版校准角色卡与示例、再加入轻量情境/意图。使用相同事实快照、模型、输出上限和历史，每组至少20个场景、每场景3次生成，离线比较，不需要启动游戏。

场景含事实问答、轻松闲聊、玩家疲惫、表达关心、不同意角色、拒绝邀约、送礼后回应、婚后日常、提起父母、重复话题、承诺跟进和含混情绪；同一问题也用于其他角色的区分性评测。

事实正确作为门槛，同时看：

- 去掉姓名，能否从态度和语言辨认角色，而不是靠反复提紫水晶/矿洞。
- 是否回应玩家这句话的人际含义，而非只回答字面数据。
- 是否有自己的偏好、打算和分歧，且不强行推进玩家不想继续的话题。
- 是否保持情绪连续、措辞变化和适当长度。
- 是否避免编造共同历史、无依据动作、套话和每轮固定反问。

人工盲评为主，模型评分辅助；单纯关键词命中和AI裁判分数都不能代替角色体验。建议进入游戏验收前，候选在盲评中优于当前版本且事实回归不退步。增加的输入长度、输出长度、P50/P95响应时间一起报告。流式显示或头像表情属于后续呈现优化，不用它们掩盖台词本身的问题。
